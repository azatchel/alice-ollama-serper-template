# Ревью безопасности и стабильности

Дата: 26 октября 2026 года. Объект: изменённый backend и настройки форка.
Метод: ручной просмотр обработчика, провайдеров, Redis Lua-скриптов, зависимостей и тестов. Это ревью исходников, не пентест развёрнутого сервиса. Проверки с настоящими ключами, Redis, Vercel и Яндексом не проводились.

## Исправлено

| Проблема исходного шаблона | Изменение |
|---|---|
| Открытый POST мог расходовать API-квоты | Обязательный случайный секрет в URL, сравнение через timingSafeEqual, проверка skill_id |
| Нет общего лимита | Redis Lua атомарно допускает один новый вопрос в 15 секунд на весь навык; отказ Redis блокирует генерацию |
| Дубликаты могли повторно вызывать модель | Последний message_id и статус задания проверяются до запуска и повторно атомарно при резервировании |
| Поиск 5 секунд несовместим с дедлайном Алисы 4,5 секунды | Быстрое подтверждение, фоновая обработка через waitUntil, получение результата репликой «ответ» |
| Клиент передавал историю | История формируется сервером и хранится в Redis, до 8 сообщений по 1200 символов |
| Нет ограничения входных данных | Проверка протокола, навыка, сессии, типа сообщения; тело до 32 КиБ, реплика до 1200 символов |
| Возможны долгие или чрезмерные ответы API | AbortController охватывает чтение тела; Serper 5000 мс, Ollama 35000 мс, Redis 750 мс; размеры тел ограничены |
| Поиск мог пропасть незаметно для модели | Явный статус недоступности поиска в контексте модели |
| Промежуточные рассуждения/ошибки могли попасть в речь | Используется только message.content, пустые и обрезанные ответы отклоняются, ошибки отображаются фиксированными фразами |
| Нет контроля зависимостей | Lockfile и точная версия SDK; npm audit --omit=dev: 0 известных уязвимостей на дату проверки |

Внешние адреса Ollama/Serper фиксированы, Redis разрешён только по HTTPS в зоне `.upstash.io`, редиректы запрещены. Код не открывает найденные ссылки, не выполняет команды модели и не даёт ей инструменты. Секреты не включаются в промпт. Сырые ошибки, запросы и ответы не логируются кодом приложения. Ключи Redis разделены по навыку и HMAC сессии. При завершении задания Lua проверяет идентификатор, чтобы старый worker не перезаписал новое задание.

## Остаточные риски и рекомендации

### Высокий приоритет: доступ к webhook и расход ресурсов

Секрет в query string — bearer credential. Он может оказаться в инфраструктурных логах, истории браузера или скриншотах. skill_id и session_id можно подделать; они не доказывают происхождение запроса. При утечке URL посторонний сможет использовать сервис в пределах общего лимита и читать результат известной сессии.

Рекомендации: случайный секрет минимум 32 символа, приватный навык, закрытый доступ к настройкам и логам, маскирование параметра token, ротация при утечке. Перед публикацией добавьте отдельный защищённый ingress и допустимые способы проверки происхождения запросов согласно актуальным возможностям Яндекса. Не полагайтесь на IP из тела или произвольного X-Forwarded-For.

Лимит защищает генерации, но не HTTP-вызовы, функцию, объём входного тела до его разбора платформой и Redis-проверки. Даже один запрос каждые 15 секунд допускает до 5760 новых вопросов в сутки при непрерывной нагрузке.

Рекомендации: WAF/rate limits на входе Vercel, дневной бюджет/kill switch, доступные ограничения расходов и уведомления у провайдеров. При росте аудитории дополнить общий лимит лимитами по пользователям. При смене WEBHOOK_SECRET HMAC-ключи меняются, поэтому текущая история и cooldown больше не доступны; учитывать при ротации.

### Высокий приоритет: доставка фоновых заданий

waitUntil не обеспечивает долговечную очередь и exactly-once. Авария между резервированием и запуском/сохранением результата оставляет pending до TTL 180 секунд. Нет автоматического повторения запроса к модели: это снижает риск двойного расхода, но не восстанавливает потерянные задания. Дедупликация действует пока существует запись последнего задания; после её удаления/вытеснения повтор может быть обработан заново. Старая завершённая запись может воспроизводиться на повторную доставку старого message_id, но не запускает модель.

Рекомендации: перед публичной эксплуатацией перейти на надёжную очередь/worker с идентификаторами заданий, явными сроками, retry policy и dead-letter queue; учитывать стоимость повторов. Для Redis выбрать режим без произвольного вытеснения ещё действующих ключей. Не использовать временные/эвиктируемые кэши для строгого лимита. При репликации проверять гарантии согласованности выбранной конфигурации.

### Средний приоритет: задержки и модель

Kimi-k2.7-code специализируется на программировании, может тратить время/токены на reasoning. Нет реальных измерений задержек и проверки доступности на аккаунте. Поиск плюс генерация могут занимать до 40 секунд, но HTTP-подтверждение их не ждёт. Нельзя гарантировать deadline Алисы при холодном старте или деградации Redis/сети.

Рекомендации: проверить сквозной сценарий после настройки; измерять p50/p95 подтверждений, время получения результата, долю ошибок, Redis latency и расходы без записи содержимого диалогов. Настроить алерты. При необходимости использовать более быструю модель; изменение модели выполнять только после проверки поддерживаемых параметров. Текущая модель сохранена по запросу пользователя.

### Средний приоритет: внешние данные и приватность

Пользовательские вопросы/история уходят в Ollama Cloud, поисковые вопросы — в Serper, ответы и история — в Redis с TTL. Промпт и JSON-разделение данных не гарантируют защиты от prompt injection. Модель может сообщать ложные факты. Детектор поискового намерения основан на регулярном выражении.

Рекомендации: не передавать чувствительные сведения; ограничить доступ к Redis и включить нужные меры защиты/хранения у провайдера, в том числе для резервных копий и логов (TTL не гарантирует удаление из backup). Для серьёзных решений сверять первоисточники; при необходимости добавить ссылки и отдельную проверку актуальности. Не добавлять выполнение действий модели без отдельной модели угроз.

### Низкий приоритет: наблюдаемость и зависимости

GET /api проверяет только жизнь обработчика. Ошибки логируются общими фразами без диагностических кодов, что ограничивает расследование. SDK закреплён на 3.6.1, поскольку 3.10.3 на дату проверки подтягивал уязвимую цепочку Zod. Нужны регулярные проверки зависимостей и обновление после устранения проблемы.

Рекомендации: защищённая проверка готовности конфигурации/провайдеров, обезличенные коды ошибок и request ID, CI с npm ci / npm test / npm audit, периодический пересмотр закреплённых версий.

## Проверки

12 автоматизированных тестов проходят: протокол и валидация, авторизация, лимит входа, асинхронный ответ, повторная доставка, общий 15-секундный интервал между сессиями, отказ Redis до запуска API, ошибки поиска и модели, скрытие reasoning, ограничение тел и таймаут, точный таймаут Serper 5000 мс с виртуальными таймерами, история/изоляция сессий, форма атомарных Redis-команд.

Ограничения тестов: Redis заменён тестовым хранилищем, Lua-скрипты проверены вручную и по форме команд, но не исполнялись на настоящем Redis. Vercel runtime, lifecycle waitUntil, реальные API и Яндекс требуют отдельной проверки. 0 npm audit findings не означает отсутствия всех возможных уязвимостей.

## Проверка перед использованием

1. Настроить отдельный Redis, все переменные и приватный навык. Не публиковать webhook URL.
2. Проверить, что POST с неверным token/skill_id не вызывает провайдеров.
3. Проверить «вопрос → подтверждение → ответ», затем второй новый вопрос раньше и позже 15 секунд, в том числе из другой сессии.
4. Проверить истечение 180-секундного TTL, недоступный Redis, неверный ключ Ollama и отказ Serper.
5. Убедиться по метрикам, что подтверждение приходит в бюджет 4,5 секунды, фон завершается до лимита функции 60 секунд, а logs не раскрывают token/тексты.
