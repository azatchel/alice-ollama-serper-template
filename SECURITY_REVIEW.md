# Ревью безопасности и стабильности

Дата: 26 октября 2026 года. Актуальная версия работает синхронно: вопрос → ответ в той же реплике, без фоновой генерации и команды «ответ».

Метод: ручной просмотр кода, настроек, Redis Lua-скриптов и автоматизированные тесты. Это ревью исходников, не пентест развёрнутого сервиса. Реальные API-ключи, Redis и Яндекс не проверялись.

## Защитные меры

- Webhook требует случайный секрет минимум 32 символа; сравнение через timingSafeEqual. Проверяется skill_id, но он не заменяет аутентификацию.
- Один новый вопрос в 15 секунд на весь навык. Lua-скрипт атомарно проверяет дубликаты и общий cooldown, получает серверную историю и резервирует слот одним HTTP-вызовом. Отказ Redis блокирует генерацию. Неудачная попытка расходует интервал; отказ по лимиту не продлевает его.
- Сохранение результата проверяет id записи (CAS), чтобы старое выполнение не перезаписало новое. Pending-запись после аварии не блокирует новый вопрос дольше общего cooldown. Дедупликация ограничена существованием записи последнего задания.
- Вход ограничен 32 КиБ и репликой 1200 символов; проверяются протокол, навык, сессия и тип сообщения. История не принимается из клиентского session_state.
- История: максимум 8 сообщений по 1200 символов, TTL 180 секунд после записи; ключи сессий — HMAC. Обновление записи продлевает TTL. Redis не получает ключи Ollama/Serper.
- Адреса Ollama/Serper фиксированы; Redis разрешён только по HTTPS в зоне `.upstash.io`, редиректы запрещены. Ответы API ограничены по объёму, включая chunked bodies; таймаут действует до конца чтения.
- Незавершённые обращения отменяются при общем дедлайне. Нет фоновых заданий, автоповторов, выполнения кода модели или переходов по найденным ссылкам.
- Используется только message.content; reasoning, сырые ошибки и ключи не озвучиваются. Пустые и обрезанные ответы отклоняются. Содержимое диалога и секреты приложение не пишет в логи.
- SDK Vercel удалён вместе с waitUntil. Сторонних runtime-зависимостей нет; npm audit не находит известных уязвимостей на дату проверки.

## Бюджет времени

Яндекс ждёт весь ответ 4,5 секунды, включая сеть и установление соединения. Приложение ограничивает собственное время 3600 мс от входа в handler, оставляя номинально 900 мс внешнего запаса. На Redis выделено по 250 мс на резервирование и сохранение, на Serper 600 мс, на Ollama до 2800 мс, но не больше остатка общего времени минус 300 мс. Общий таймер не позволяет суммированию отдельных стадий превысить бюджет. При его срабатывании возвращается короткий ответ о таймауте и отменяются текущие HTTP-вызовы.

Это бюджет приложения, а не гарантия доставки Яндексу за 4,5 секунды: холодный старт до входа в handler, сеть, задержка event loop и инфраструктура вне его контроля. Короткий таймаут Serper повышает вероятность отсутствия свежего поиска. Kimi-k2.7-code может не успеть сформировать ответ за оставшееся время.

## Остаточные риски и рекомендации

### Высокий приоритет: доступ и расходы

Секрет в query string — bearer credential: он может попасть в инфраструктурные логи, историю браузера или скриншоты. При утечке адреса посторонний сможет расходовать ресурсы в пределах лимита. skill_id/session_id подделываются и не доказывают происхождение запроса.

Используйте приватный навык, случайный секрет, маскирование token в инфраструктуре, ограниченный доступ к настройкам/логам и ротацию при утечке. Перед публичным запуском добавьте защищённый ingress и допустимую проверку происхождения запросов по актуальным возможностям Яндекса. Не доверяйте IP из тела или произвольного X-Forwarded-For. Ротация WEBHOOK_SECRET меняет HMAC-ключи, поэтому текущие история/cooldown становятся недоступны.

Глобальный лимит ограничивает новые генерации, но не HTTP/Redis-вызовы и обработку входа платформой. При непрерывной нагрузке допускается до 5760 вопросов в сутки. Нужны WAF, дневной бюджет/kill switch и доступные лимиты/уведомления расходов у провайдеров. При расширении аудитории добавьте пользовательские лимиты.

Redis должен быть постоянным, без произвольного вытеснения действующих ключей. Проверяйте гарантии согласованности выбранной конфигурации. Истечение/потеря записи ограничивает дедупликацию; отменённый HTTP-запрос не гарантирует отмены вычисления/списания на стороне провайдера.

### Высокий приоритет: скорость модели

Функционально ответы выдаются в той же реплике. Успешная генерация Kimi за короткий срок пока не подтверждена реальными измерениями. Reasoning может потреблять токены и время. Модель сохранена по запросу пользователя; неподтверждённое отключение thinking не используется.

После развёртывания измерьте p50/p95 задержки полного ответа, долю таймаутов и качество поиска на обычных голосовых вопросах. Убедитесь, что Redis расположен рядом с регионом функции. Если Kimi регулярно не успевает, потребуется более быстрая модель или другой способ получения актуального контекста; увеличение таймаута не решает лимит Яндекса.

### Средний приоритет: сохранение и восстановление

Если запись результата не удалась, готовый ответ всё равно возвращается пользователю. При этом история/кэш могут остаться прежними. Авария после резервирования расходует 15-секундный интервал, но последующий новый вопрос после cooldown допустим. Последний повторённый message_id не запускает модель заново, пока запись существует. Автоповторов платных вызовов нет.

Проверяйте отказы Redis и повторные доставки после развёртывания, настройте обезличенные метрики ошибок. GET /api — только liveness, не проверка готовности всех провайдеров.

### Средний приоритет: данные и достоверность

Ollama Cloud получает вопрос и историю, Serper — текущий поисковый вопрос, Redis — ответ/историю с TTL. TTL не гарантирует удаления из backup или инфраструктурных журналов. Не передавайте чувствительные сведения, настройте доступ и хранение данных у провайдеров.

Поиск работает по ключевым словам и кратким описаниям трёх результатов. Модель может пропускать актуальность или сообщать ложные факты. JSON-разделение данных и системный промпт не гарантируют защиты от prompt injection. Для серьёзных решений сверяйте первоисточники. Не добавляйте выполнение действий модели без отдельной модели угроз.

## Проверки

14 автоматизированных тестов проходят: валидация/авторизация, прямой ответ в исходном HTTP-запросе, протокол Ollama и поиск, общий 15-секундный интервал между сессиями, дедупликация, история, отсутствие специальной команды «ответ», отказ Redis до/после генерации, ошибки провайдеров, скрытие reasoning, ограничение тел/таймауты, отмена Serper на 600 мс и общий дедлайн 3600 мс при зависшей модели или хранилище, формат Lua-команд и HMAC-изоляция и диагностика конфигурации без раскрытия секретов.

HTTP и Redis в тестах подменены. Таймеры бюджета проверяются виртуальным временем. Lua проверен вручную и по форме команд, но не исполнялся на настоящем Redis. Реальные задержки, доступность модели, поведение Vercel и голосовой диалог требуют проверки после настройки.

Перед эксплуатацией: проверить «вопрос → ответ» на колонке; второй вопрос раньше/позже 15 секунд из разных сессий; неверный token/skill_id; отказ поиска/модели/Redis; истечение TTL; сетевые задержки и отсутствие token/диалогов в журналах.
